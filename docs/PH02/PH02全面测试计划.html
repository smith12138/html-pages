二、测试方式分层（谁来测）

- [自动] 接口 + DB 断言（框架 pytest）：功能正向、边界、异常校验、鉴权/RBAC、业务规则、数据一致性、并发竞态、轻量性能（P95 单接口）、部分安全（IDOR/越权/注入/幂等）。主力。 - [浏览器] 我驱动 in-app 浏览器：UI 展示/交互、前端校验提示、富文本渲染、脱敏展示、跳转。较慢，抽查关键。 - [人工] 我做不了、需人工：真实支付网关回调(URL 型充值到账)、真实短信/邮件 OTP 接收、大并发压测(避免打爆测试环境)、Google 2FA 绑定流程、视觉像素级 UI、需多真人多设备的场景。→ 记「待人工」清单。

⚠ 四.5、待人工/待专项清单（我做不了，必须人工或专用环境）

这些是环境/流程限制导致我无法自动化验证的部分，需人工介入。 1. 真实充值到账全链路 —— 充值通道为 URL 型第三方网关(PH_MOCKPAY/Monkpay/EZPAY)，staging 无支付回调；创建充值单成功但永远停在待处理/失败，无法验证到账入账、幂等回调。→ 需 mock 网关回调或真实小额支付。 2. 真实出款代付到账 —— 出款审核 approve 后 status→301(审核通过/代付中)，EZPAY 代付在 staging 无回调，停在 301 不到账。→ 需 mock 代付回调。（审核流转本身已验证） 3. 真实短信/邮箱 OTP 收码 —— 注册 OTP、change-password-by-code 改密验证码、短信 send-code。→ 需真实收码（短信真实发送会触达真号+计费，未自测）。 4. Google 2FA 绑定流程 —— 测试环境未开 2FA，superAdmin 无需 totp。→ 需开启后人工绑定验证。 5. 大并发压测（吞吐/稳定性/容量） —— 计划只做小并发(5-20)验正确性，不打爆共享环境。→ 真压测需专用环境。 6. RBAC 越权/最小权限 —— 现有 smith001/smith002/superAdmin 均全权限，无受限角色账号，无法测低权限越权(403)。→ 需人工建受限角色账号。 7. 客服 Live Chat —— Support 弹窗的 Live Chat 需真人客服会话。→ 人工。 8. 视觉像素级 UI / 多真机多设备 —— 精确视觉、真机适配、多设备并发场景。→ 人工。 9. RTP 统计显著性 —— RTP 需数千局才有统计意义；已验证注单/账本对数一致，但 RTP 数值需大样本。→ 专项大样本。

五、安全测试要点（横切，每模块带）

越权/IDOR（换 user_id/order_id 访问他人）、RBAC（低权限调高权限接口应 403）、鉴权（无 token/过期）、注入（SQL/XSS 尝试）、幂等（重复/重放）、敏感信息脱敏与密钥展示门控、金额篡改/负数/精度、批量与竞态。

六、性能测试口径（克制，勿打爆测试环境）

- 单接口 P95/P99 延迟基线（列表/审核/充提）：小样本(20-50 次)测延迟，不做大并发压测。 - 大分页/深翻页正确性与耗时。 - 并发竞态用小并发（5-20）验正确性，非压测。 - 真·压测（高并发/吞吐/稳定性）→ 待人工/专用环境（避免影响共享测试环境与真实数据）。
