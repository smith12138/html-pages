 P2 造首充VIP0号铺够quota(≥100可提2单50)+设资金密码+绑卡。①串行验上限:逐单POST /api/v1/user/withdraws{amount:50,...}→第1单200 OK、第2单400 WITHDRAW_DAILY_COUNT_EXCEEDED(证VIP0每日上限=1)。②并发绕过:换同类0历史号,ThreadPoolExecutor 2线程同时发2单(各独立Idempotency-Key)→两单均200 OK、DB落2笔。 无论串行还是并发提交,单日提现单数都不得超过VIP档位上限(VIP0=1);每日次数校验应原子/串行化(如DB行锁或唯一约束),并发下也精准拦截,超出的应返 WITHDRAW_DAILY_COUNT_EXCEEDED。 实测:干净号uid13960串行→第1单200/第2单400 DAILY_COUNT_EXCEEDED(上限=1确立);uid13976(0历史,quota117)并发2单→(200 OK,200 OK)、DB落2笔;uid14021并发3单→2单200(第3单WITHDRAW_QUOTA_INSUFFICIENT,受quota非次数限制)。→每日次数校验是read-then-check非原子,并发请求都在计数自增前读到count<上限而全部放行(TOCTOU竞态)。资金侧安全:每单仍受quota/本金约束(无双花,前已验),但绕过每日提现次数=风控/velocity限制形同虚设,可被拆多单并发提交规避人工复核阈值/反洗钱速率监控。建议:提现落单前对(user,自然日,马尼拉时区)做原子计数(行锁/唯一约束/串行化),或提交入队串行处理。 【严重度】高quota号(quota387)并发发12单→7单成功(3 DAILY_COUNT_EXCEEDED+2 QUOTA_INSUFFICIENT),DB落7单/6待处理。即每日次数上限=1被一次并发爆发放行7单,唯一真实约束是quota(7×50=350≤387,第8单起才被quota拦)——每日次数控被完全击穿,可拆到quota上限的单数并发规避。落败的3单才看到已自增计数。 待处理 Smith
