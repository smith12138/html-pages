PH01 提现限制调整 · 需求文档（草案）

基于运营参考稿 + 测试环境后台/前端实测整理 · 供产品/研发/运营对齐 · 待确定点见第六节
阅读须知：本文是讨论草案，不是最终需求。其中「现状」为测试环境实测结论；「拟定规则」需产品拍板；「待确定点」必须先定清楚再进入开发。运营原稿仅作参考，本文已对其中不准确处做了修正。

一、背景与目标

背景：现行提现按 VIP 等级限制每日次数（VIP0 每天只能提 1 笔），用户体验较差。

目标：变更 去除每日次数限制；新增 按 VIP 等级的每日累计金额限额；超限时按场景精确弹窗提示，并提供便捷操作（填入剩余额度 / 提升 VIP）。

二、现状说明（实测，作为需求前提）

⚠️ 提现有「两道独立闸门」，缺一不可通过（现状）：
闸门 A · 可提额度（打码流水）：可提额度 = min(本金可用, 打码换来的 quota)。礼金不可提。这是 H5 上大字展示的「Available to withdraw」，也是用户当前最常撞到的那道。实测某号：可提额度仅 ₱363.68，本金有 ₱11.4 万。
闸门 B · 限额：现为「VIP 分档每日次数」+「全局每日金额 200,000」。本次要改的是这道。

三、拟定规则（需产品确认）

3.1 限额口径

  • 去除 VIP 每日次数限制。
  • 新增 VIP 分档「每日累计金额限额」（新配置，各档数值待定，见 6.1）。
  • 已用额度（当日） = 今日已成功提款金额 + 处理中/审核中订单金额（防绕过，处理中计入）。
  • VIP 当日剩余 = max(0, VIP当日金额上限 − 已用额度)。

3.2 最终「可提金额」= 两道闸门取小

核心：用户实际可提 = min（闸门A 可提额度[打码], 闸门B VIP当日剩余[金额]）。H5 的「Available to withdraw」应展示这个最终值；超限弹窗必须能区分是哪道闸门拦的（打码没够 vs VIP 额度超）。

3.3 额度恢复（需确认，见 6.2）

  • 处理中订单：先计入已用额度（占用）。
  • 该订单最终成功/已付：额度维持占用。
  • 该订单被拒绝/出款失败退回：拟自动恢复对应金额到当日额度。与现状不同（现状被驳回仍占用、不退）。

3.4 保留项

  • 保留 最小提现额 50、单笔上限、待处理单上限 10、首充限额、马尼拉自然日重置。

四、场景与弹窗（修正版 · 覆盖两道闸门 · 英文文案待定稿）

下列为逻辑与文案示意；正式英文文案见 6.7。运营原稿只覆盖「VIP 金额」这一道，本文补齐「打码闸门」相关场景。

场景 0（新增·打码没够）：VIP 额度还有，但可提额度(打码) < 申请额
→ 提示「需完成打码要求才能提取，当前可提 ₱XXX（差 ₱YYY 流水）」，引导去投注/查看打码进度，不要误导成"VIP 额度不足"。
场景 1（未提过·单笔超 VIP 日限）：今日已用 0，单笔 2000 > VIP 日限 1000
→ 「当前 VIP 每日提款上限 ₱1,000，本次已超限，请修改金额或提升 VIP。」 [修改金额][提升 VIP]
场景 2（累计超限·最常见）：今日已用 500，再提 600，累计 1100 > 1000
→ 「当前 VIP 每日上限 ₱1,000，今日剩余可提 ₱500，请修改金额或提升 VIP。」 [填入剩余额度→自动填 500][提升 VIP]
注：「剩余」应是两道闸门取小后的值，不只是 VIP 剩余。
场景 3（额度用完）：今日已用 1000，剩余 0
→ 「今日提款额度（₱1,000）已用完，请明日再试或提升 VIP。」 [我知道了][提升 VIP]
场景 4（处理中占额度）：有 800 处理中，再提 500，已用 800+500=1300>1000
→ 「今日剩余可提 ₱200（含处理中订单），请修改金额或提升 VIP。」 [修改金额][提升 VIP]
场景 5（拒绝/失败恢复）：处理中 800 被拒/失败退回 → 当日已用恢复、剩余回到 1000，正常提交无弹窗。需研发实现恢复逻辑
场景 6（跨零点）：按马尼拉 00:00刷新当日已用为 0；昨日用尽、今日 00:01 可正常提。
场景 7（VIP 变更）：
7a 升级：剩余实时重算 = 新上限 − 已用，可继续提。注意：VIP 升级需「充值 AND 投注」双阈值达成，非充值即升（见 6.8）。
7b 降级：剩余 = max(0, 新上限 − 已用)，超了则阻断（触发场景 3）。

五、与运营原稿的差异修正（避免照抄）

  1. 运营称"按 VIP 限制次数和金额" → 现状只有 VIP 次数、没有 VIP 金额；本次是「去次数 + 新增 VIP 金额」两件事。
  2. 运营举例限额 1000P → 现状全局是 200000；VIP 各档金额是全新要定的数。
  3. 运营"充值后升 VIP" → 实测需充值+投注双阈值，文案别误导。
  4. 运营"拒绝/失败恢复额度" → 现状不退，属新增逻辑。
  5. 运营"自然日 00:00" → 必须写明马尼拉时区。
  6. 运营通篇忽略了打码闸门（可提额度）——而这正是 H5 上用户最常撞到的那道。

六、待确定的点（开发前必须拍板）

6.1 VIP 各档每日金额上限具体数值？（VIP0 ~ VIP9 分别 = ?）——运营/产品定；建议同时定「是否单笔上限也随 VIP 变」。
6.2 拒绝/失败是否恢复额度？现状不退。若要退：出款失败、人工拒绝、用户撤单 三种情况是否都退？退的时点（拒绝即退 vs 到终态才退）？
6.3 「处理中」计入已用额度——确认口径：pending_review / risk_review / approved / paying 哪些状态算"处理中占额度"？
6.4 两道闸门如何在 H5 呈现与区分？「Available to withdraw」显示 min(打码可提, VIP当日剩余)？两种超限弹窗文案分别怎么写、怎么判断该弹哪个？「填入剩余额度」填的是哪个剩余（应是取小后的）？
6.5 去掉次数后的防刷/审核压力——只留金额、可无限次拆分小额（如 1000 拆 20 笔 50）。是否需要其他限制（如单日笔数软上限、单笔下限提高、待处理上限收紧）？人工审核量激增，风控/财务先评估。
6.6 是否彻底去次数、还是保留一个很大的次数上限兜底？（如保留 daily_max_count=20 防极端刷单）
6.7 文案语言与定稿——H5 是英文，需英文（是否还要他加禄语？）全套弹窗文案定稿；「提升 VIP」按钮跳转到哪个页面。
6.8 「提升 VIP」的引导口径——VIP 升级需充值+投注双阈值，不能让用户以为"充钱就能提更多"；文案/引导如何表达真实门槛。
6.9 VIP 变更时额度实时性——升/降级后当日剩余是否立即重算生效？（实测 VIP 评定近实时，但需确认限额随之实时）
6.10 首充限额、单笔上限是否保留/随 VIP 调整？与 VIP 日金额限额的优先级/叠加关系？
6.11 配置落位——VIP 金额上限加在 vip_levels 新字段，还是独立 VIP 提现策略表？是否要后台可配（运营自助改各档数值）？

七、建议实施顺序

  1. 先定 6.1（各档数值）+ 6.2/6.4（恢复规则、双闸门呈现）这三个关键点。
  2. 后端：加 VIP 金额限额字段 + 停用次数限制 + 已用额度（含处理中）计算 + 恢复逻辑。
  3. 前端 H5：Available 展示取两闸门小值 + 各场景弹窗（英文）+ 填入剩余/提升 VIP 按钮。
  4. 测试重点：两闸门取小、处理中占额度、拒绝恢复、跨马尼拉零点、VIP 升降级实时、并发拆单不超额。
